# From drone video to a dot on the map

Start with **30 frames over one known site**. Give the computer the video, the camera calibration, an overhead photo, and a grid of surface heights. Ask it to mark where the camera was at each frame. The first result worth keeping is one estimated position, the image matches that produced it, and its error against a withheld position.

OrthoTrack already does jobs 3 through 6. For the first demo, most of your work is choosing usable data, checking the coordinates, and connecting the results to your player. [OrthoTrack](https://github.com/cvg/orthotrack)

## The jobs in build order

An **overhead photo** here means an orthophoto. Every pixel has a map location. A **surface height grid** (DSM) gives the elevation at that location, including roofs. Together they turn a roof corner seen on the map into a point measured in meters.

| Job | Input | Output | Fast baseline | One quick improvement |
| --- | --- | --- | --- | --- |
| 1. Prepare one site | An overhead RGB image, a height raster, and their coordinate metadata | A map where a valid pixel can be looked up as `east, north, elevation` in meters | Use the paired map files in one MovingDrone scene. No model needed. | Check one identifiable point and one missing-height pixel before debugging any camera code. [Scene format](https://github.com/cvg/orthotrack/blob/main/dataset/movingdrone.md) · [GDAL pixel coordinates](https://gdal.org/en/stable/tutorials/geotransforms_tut.html) |
| 2. Read the footage | MP4 and camera calibration for that resolution and zoom | RGB frames, each with a frame ID, capture time in seconds, and lens parameters | Use the bundled video and intrinsics. For your own MP4, read presentation timestamps with PyAV. | If you resize a frame, scale the focal lengths and principal point with it. Check that pausing the video selects the same frame as the pose log. [OrthoTrack custom inputs](https://github.com/cvg/orthotrack) · [PyAV time](https://pyav.org/docs/stable/api/time.html) |
| 3. Find the right map area | One video frame and the site map | One or several candidate map crops, each with a location on the map | Start with one known site tile. Let OrthoTrack search it. | When the site grows, try pretrained MegaLoc. Cache one descriptor per tile and return the top five. Keep it only if the correct area appears in the shortlist on held-out aerial frames. [OrthoTrack method](https://orthotrack.ethz.ch/) · [MegaLoc](https://github.com/gmberton/MegaLoc) |
| 4. Find the same landmarks | A video frame and one candidate crop | Pairs of pixels such as “this roof corner in the frame is that corner on the map” | OrthoTrack already uses pretrained RoMaV2. For a CPU baseline, use OpenCV SIFT and nearest-neighbor matching on a small reference bank. | If matching takes too long, compare DISK + LightGlue on the same image pairs. Draw the accepted matches on both images. [RoMaV2](https://github.com/Parskatt/RoMaV2) · [LightGlue](https://github.com/cvg/LightGlue) |
| 5. Locate the camera | Matched pixels, surface heights, and camera intrinsics | Camera center `x, y, z` in meters, a 3D rotation, and the matches supporting that pose | Look up each map pixel in the DSM. Feed the resulting 3D points and their video pixels to OpenCV `solvePnPRansac`. OrthoTrack handles this step. | Project the 3D points back onto the frame. Reject a pose if the agreeing points cluster on one small patch or their pixel errors are too large. [OpenCV pose solvers](https://docs.opencv.org/4.x/d5/d1f/calib3d_solvePnP.html) |
| 6. Follow the flight and recover | Last frame’s verified landmarks and the next video frame | A new camera pose or a `lost` record at that timestamp | Lucas-Kanade optical flow follows the pixels. Their map coordinates stay fixed, so the same pose solver works again. When tracks fail, search the map again. | Mask a short section of the video. Show a gap during loss and measure seconds to the first correct fix after the image returns. [OrthoTrack tracker](https://github.com/cvg/orthotrack) · [OpenCV optical flow](https://docs.opencv.org/4.x/dc/d6b/group__video__track.html) |
| 7. Put it on Earth | Camera pose, map coordinate system, origin offset, vertical datum, and timestamps | Latitude and longitude in degrees, named sea-level height in meters, and course in degrees true | Restore any map offset. Use pyproj for geographic coordinates. If the source uses ellipsoidal height, convert it with the appropriate geoid grid. Calculate course from successive horizontal positions. | Check one known elevation. Leave sea-level height empty when its reference is unknown, and course empty when hovering. Airframe heading requires the camera-to-body orientation, including a moving gimbal. [pyproj](https://pyproj4.github.io/pyproj/stable/api/transformer.html) · [GeographicLib heights](https://geographiclib.sourceforge.io/html/GeoidEval.1.html) |
| 8. Score and replay it | Timestamped estimates, video, and a separate file of reference positions | A replay with a moving marker and a scorecard | Join on frame ID or capture time. Show median horizontal error, median absolute height error where the datums agree, and the fraction of frames with a fix. Count every lost frame in coverage. | Scrub to the worst accepted fix and show its matches. Add the 95th-percentile error and processing time per frame. The existing Groundframe mockup already has a timeline and status display. [Groundframe mockup](../groundframe-demo/groundframe.html) |

## The first afternoon

1. **Get a path on screen.** Use OrthoTrack’s published one-scene download and first-run example. Run with `--end_frame 30 --save_keyframe_vis`. Open `tracking_results.png`, one match image, and `results.csv`. The authors also provide a hosted demo. Their local dense matcher requires CUDA and they recommend `turbo` for about 8 GB of VRAM. MovingDrone’s bundled footage is rendered. Label this run accordingly. [First-run instructions](https://github.com/cvg/orthotrack) · [Hosted demo](https://huggingface.co/spaces/ussaema/orthotrack-demo)
2. **Check the output is yours.** The runner writes both `est_*` and `gt_*` columns. Drive the marker from successful visual estimates and inspect the `method` field. Display prediction-only periods separately or leave a gap. Keep `gt_*` for the scorecard. For a blind run, use the custom-footage entry point with a fixed site map, omit `--gt_poses`, and leave simulated sensor priors off. [Runner and CSV fields](https://github.com/cvg/orthotrack/blob/main/scripts/run_tracking.py)
3. **Try a real recording.** Pick a short downward-looking survey clip with independently collected map coverage. A public research option is a UAVScenes run with an overlapping map built from other runs. Check the map’s contributing sequences first. The authors reconstructed groups of runs together and the data terms specify academic use. Use actual capture times and score the whole chosen interval. UAVD4L’s spaced stills are better suited to the one-image test. [UAVScenes data and terms](https://github.com/sijieaaa/UAVScenes) · [Map construction, section 3](https://openaccess.thecvf.com/content/ICCV2025/papers/Wang_UAVScenes_A_Multi-Modal_Dataset_for_UAVs_ICCV_2025_paper.pdf) · [UAVD4L acquisition](https://arxiv.org/abs/2401.05971)

**For a startup deliverable or a machine without CUDA:** OrthoTrack’s code carries CC BY-NC 4.0. Start with OpenCV SIFT, PnP and optical flow on imagery you have rights to use. The first learned matcher I would try on CPU is XFeat. Its authors ship a two-image notebook and demonstrate sparse matching on a laptop CPU. Swap just the matcher and compare correct poses per minute on your clip. For a first real-image fix, CrossLoc already supplies real drone photos and synthetic references with known 3D coordinates. Use independently sampled `train_sim` references with a real validation query. Its paired test render would give away the test viewpoint. [OrthoTrack license](https://github.com/cvg/orthotrack/blob/main/LICENSE) · [OpenCV](https://github.com/opencv/opencv) · [XFeat](https://github.com/verlab/accelerated_features) · [CrossLoc data layout](https://github.com/TOPO-EPFL/CrossLoc-Benchmark-Datasets)

## The upgrade I would show

**Pause the video and project building outlines over the actual roofs.** The input is a verified camera pose, its calibration, and a building mesh in the same map frame. The output is an overlay anyone can judge by eye. OrthoTrack ships a visualization script for this. If the scene has no building mesh, use its saved match image beside the frame. Both work before you have a Gaussian splat. [Overlay script](https://github.com/cvg/orthotrack/blob/main/scripts/visualize_results.py)

**If a same-site splat is available, add a wipe between real and rendered views.** Give gsplat the aligned splat, estimated camera pose, and intrinsics. Render one RGB image from that viewpoint. If the largest errors persist even when landmark matches are correct, test GS-CPR on a few frames with the same starting poses and compare position error before and after. Its released pipeline expects compatible scene assets and coarse poses. That makes the wipe the cheaper first experiment. [gsplat renderer](https://docs.gsplat.studio/main/apis/rasterization.html) · [GS-CPR](https://github.com/XRIM-Lab/GS-CPR)
